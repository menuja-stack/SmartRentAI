## Service 1: Recommendation Engine (Profile-Based "For You")

| Field | Value |
|-------|-------|
| **Port** | `:8001` |
| **Files** | `app.py` (Flask) · `recommender.py` (inference core) |
| **Status** | **Trained** — two saved model files |
| **Algorithm** | Two-stage hybrid: supervised profile→criteria + priority-weighted similarity |
| **Model files** | `profile_model.joblib` (~350 MB) · `property_features.joblib` |
| **Training scripts** | `generate_dataset.py` → `build_property_features.py` → `train_profile_model.py` |
| **Evaluation script** | `evaluate_model.py` (loads the saved models, reconstructs the identical held-out test split — does not retrain) |

### How it works (two stages)
**Stage 1 — Profile → ideal criteria (supervised)**
- Input: profession, age_group, family_size, has_children, has_vehicle, budget,
  current-district tier, preferred_type, 5 lifestyle priorities (1–5).
- Output: `matched_property_type`, `matched_district_tier` (classifiers) +
  `min_saferent_score`, `max_price`, `min_bedrooms`, `transport_score_min`,
  `hospital_score_min` (one RandomForest regressor per target).
- Trained on **10,000 synthetic rows** that encode Sri-Lankan rental domain rules.

**Stage 2 — Criteria → properties (priority-weighted similarity)**
- Each property gets a 0–1 satisfaction score per dimension (meets a minimum → 1.0;
  within budget → 1.0), weighted by the user's priority ranks, combined as a
  magnitude-aware cosine to the "fully-satisfied" ideal. Handles minimum/maximum
  threshold semantics and missing inventory types gracefully.
- Budget penalty for over-budget listings; preferred-district boost; scores clipped 0–1.

**Cold start**: missing priorities are filled from profession defaults
(`PROF_DEFAULT_PRIORITIES` in `recommender.py`).

### Metrics (Stage 1, 80/20 split on 10k synthetic — reconstructed & verified via `evaluate_model.py`)
| Target | Type | Metric |
|--------|------|--------|
| matched_property_type | classifier | F1 (macro) = 0.735, acc = 0.805 |
| matched_district_tier | classifier | F1 (macro) = 0.813, acc = 0.827 |
| min_saferent_score | regressor | MAE = 2.55 (4.1% of range) |
| max_price | regressor | MAE = 140.9 LKR (≈0.01% of range) |
| min_bedrooms | regressor | MAE ≈ 0.00 (≈0% of range) |
| transport_score_min | regressor | MAE = 2.48 (4.0% of range) |
| hospital_score_min | regressor | MAE = 2.35 (3.6% of range) |

Feature importance confirms the model learned the rules: `priority_safety`→saferent,
`priority_hospital`→hospital, `budget`→max_price (see `fig_feature_importance.png`).

**Honest caveat (for the viva)**: `max_price` and `min_bedrooms` scoring near-zero error
is a **synthetic-data artifact**, not evidence of real-world matching quality — those two
targets are near-deterministic functions of `budget`/`family_size` in
`generate_dataset.py`'s domain-rule generator, so an RF learns them almost perfectly by
construction. State this yourself in the report rather than presenting it as an
unqualified result — the classifier and safety/transport/hospital regressor scores are
the more meaningful numbers here since they involve genuine ranking uncertainty.

### Evaluation outputs (`outputs/`, generated by `evaluate_model.py`)
`fig_confusion_matrices.png` (both classifiers) · `fig_regression_mae.png` (all 5
regressors, MAE as % of range) · `fig_regression_scatter.png` (predicted vs actual for
`max_price` / `min_saferent_score`) · `fig_feature_importance.png` ·
`table_evaluation_report.txt`

### Endpoints
| Method | Path | Description |
|--------|------|-------------|
| POST | `/recommend` | Profile → top-k ranked properties + match reasons + summary |
| GET | `/recommend/profile-insights/:user_id` | What the model inferred for a user |
| GET | `/health` | Service health check (`model_trained` flag) |

### POST `/recommend` payload
```json
{
  "user_id": 5, "profession": "Doctor", "age_group": "36-45",
  "family_size": "Small Family", "has_children": true, "has_vehicle": true,
  "current_district": "Gampaha", "budget": 150000,
  "priority_safety": 5, "priority_price": 3, "priority_transport": 4,
  "priority_hospital": 5, "priority_space": 4,
  "preferred_type": "house", "preferred_districts": "Colombo,Gampaha", "top_k": 10
}
```
Response: `{ recommendations: [{ property_id, match_score, title, district, price,
bedrooms, saferent_score, match_reasons: [...] }], criteria, profile_summary }`.

### Feedback loop (Phase 7)
`update_preferences.py` reads view/save/enquiry signals from `search_history` and
re-weights each user's `priority_*` scores (action weights view=1, save=3, enquiry=5).
Run on demand or via cron: `python update_preferences.py --commit`.

## Service 2: Price Prediction

| Field | Value |
|-------|-------|
| **Port** | `:8002` |
| **File** | `ai-services/price-prediction/app.py` |
| **Status** | **Trained on REAL data** — retrained 2026-08-29 |
| **Algorithm** | CatBoost (won a 3-model comparison — see below) |
| **Model file** | `ai-services/price-prediction/price_model.joblib` |
| **Encoder file** | `ai-services/price-prediction/encoders.joblib` |
| **Scaler file** | `ai-services/price-prediction/scaler.joblib` |
| **Training script** | `train.py` (offline — run manually, not via an API endpoint) |
| **Evaluation script** | `evaluate_model.py` (loads the saved model, reconstructs the held-out test set, produces report figures — see below) |

### Training Data
- **Real scraped/manual data** from the `properties` table joined to `locations`
  (`district, city, property_type, bedrooms, bathrooms, furnished, area_sqft, latitude, longitude`
  → `monthly_rent`), filtered to `status = 'available'`.
- **1,060 rows fetched** → `area_sqft` dropped (0.1% coverage) → IQR outlier filter on
  price removes ~10% → **957 rows clean** → 820 rows survive the final feature-column
  `dropna()` used for modelling (Train 656 / Test 164, 80/20 stratified by district).
- Zero-value `bedrooms`/`bathrooms` (≈26% of rows) imputed with the **district median**.
- `latitude`/`longitude` (43% raw coverage) imputed with the **district median** coordinate;
  the trained encoders also store a **district → centroid lat/lng lookup** so `/predict`
  requests (which only ever send a district name, never raw coordinates) can still use
  lat/lng as a feature at serve time.
- No synthetic data is used anywhere in this model — 100% real listings.

### Feature Selection (data-driven, in `train.py` STEP 3)
Candidate features are kept only if `|corr(feature, monthly_rent)| ≥ 0.05` and pairwise
correlation with another kept feature is `< 0.85` (drops the weaker of the pair). For the
current dataset, all 7 candidates survived:

| Feature | \|corr\| with price |
|---------|---------------------|
| `district_enc` (target-encoded) | 0.56 |
| `property_type_enc` | 0.30 |
| `bathrooms` | 0.29 |
| `longitude` | 0.28 |
| `latitude` | 0.23 |
| `bedrooms` | 0.19 |
| `furnished_num` | 0.08 |

### Model Comparison (`train.py` STEP 5–6 — Optuna-tuned, 5-fold CV)
| Model | MAE (LKR) | RMSE (LKR) | Test R² | CV R² (± std) |
|-------|-----------|------------|---------|----------------|
| XGBoost | 90,503 | 129,145 | 0.4856 | 0.4646 ± 0.0458 |
| GradientBoosting | 91,256 | 130,889 | 0.4716 | 0.4550 ± 0.0466 |
| **CatBoost (winner)** | 91,679 | 131,227 | 0.4689 | **0.4711 ± 0.0483** |

CatBoost is selected by **CV R² (the robust, less split-dependent metric)**, not raw
test R² — XGBoost has a marginally higher single-split R² but a lower and less stable
CV score. CatBoost also handles `district`/`property_type` as **native categoricals**
via a `Pool` (no target-encoding/scaling needed for those two columns), which is the
methodological reason it's included as a third comparison model.

**Feature importance (CatBoost):** district 27.2% · bathrooms 22.7% · property_type 19.5%
· bedrooms 14.9% · latitude 7.3% · furnished 6.9% · longitude 1.5%.

### Honest limitation (for the viva)
R² ≈ 0.47 is modest and expected: `area_sqft` had to be dropped entirely (99.9% null in
the live DB), 26% of bedroom/bathroom values were imputed rather than observed, and only
820 real rows are available across ~18 districts. The model still gives a useful **price
range** estimate (see `/predict`'s `confidence_interval`), not a precise point value —
this is documented in `train.py`'s own end-of-run notes and should be stated as a known
limitation, not hidden.

### Input Features (current, real-data model)
| Feature | Type | Notes |
|---------|------|-------|
| `district` | categorical | target-encoded (mean rent) for XGB/GBR; native string for CatBoost |
| `property_type` | categorical | LabelEncoder for XGB/GBR; native string for CatBoost |
| `furnished` | ordinal | unfurnished=0, semi-furnished=1, furnished=2 |
| `bedrooms` | int | district-median-imputed where 0 |
| `bathrooms` | int | district-median-imputed where 0 |
| `latitude` / `longitude` | float | district-centroid-imputed where missing |

### Endpoints
| Method | Path | Description |
|--------|------|-------------|
| POST | `/predict` | Predict rent for given features (district, property_type, bedrooms, bathrooms, furnished) |
| GET | `/model-info` | Model name, metrics, feature list, district price ranking, EDA notes |
| GET | `/health` | Service health check |

> There is **no `/train` endpoint** in the current version — retraining is done offline
> by running `python train.py` (reads live DB → writes `price_model.joblib` +
> `encoders.joblib` + `scaler.joblib` + `outputs/*.png`), then restarting the service.

### Evaluation outputs (`outputs/`, generated by `evaluate_model.py`)
`correlation_heatmap.png` · `feature_importance.png` · `fig_model_comparison.png`

## Service 3: Chatbot

| Field | Value |
|-------|-------|
| **Port** | `:8003` |
| **File** | `ai-services/chatbot/app.py` |
| **Status** | Trained (small hand-authored dataset — see honest limitation below) |
| **Algorithm** | `TfidfVectorizer(ngram_range=(1,2), max_features=5000)` → `MultinomialNB(alpha=0.5)`, in an sklearn `Pipeline` |
| **Model file** | `ai-services/chatbot/chatbot_model.joblib` (auto-trained on first import if missing) |
| **Evaluation script** | `evaluate_model.py` (does not retrain or touch `app.py` — see below) |

### Training data
**53 hand-written examples across 10 intents**, defined inline as `TRAINING_DATA` in
`app.py` (no separate dataset file):

| Intent | Examples | Intent | Examples |
|--------|----------|--------|----------|
| `rental_pricing` | 6 | `booking_assistance` | 5 |
| `property_recommendation` | 6 | `general_faq` | 5 |
| `landlord_support` | 6 | `lease_information` | 5 |
| `account_issues` | 6 | `greeting` | 4 |
| `nearby_facilities` | 6 | `farewell` | 4 |

`app.py` fits the pipeline on **all 53 examples with no held-out test set** — there is
no train/test split in the production training code.

### Honest evaluation (for the viva) — why CV, and what it found
Since the deployed model has no held-out set, `evaluate_model.py` builds one the
statistically defensible way for a dataset this small: **4-fold stratified
cross-validation** (4 is the max fold count the smallest class — `greeting`/`farewell`,
4 examples each — supports), evaluating every example exactly once out-of-fold with the
identical pipeline architecture used in `app.py`.

**Result: accuracy 41.5%, F1 (macro) 0.34** — the weakest of the four services. The
confusion matrix shows heavy misclassification toward `landlord_support`: short, generic
phrases ("thank you", "hello") give TF-IDF very little signal with only 4–6 examples per
class, and several intents share common words ("how", "I", "property"). **Report this
finding directly rather than hiding it** — it's the concrete evidence for why a future
upgrade to sentence-transformer embeddings + a much larger training corpus (see TODO.md)
is worth doing, not a hypothetical nice-to-have.

### What it does
- Classifies user message into one of the 10 intents above (confidence < 0.25 falls back to `general_faq`)
- Returns a templated reply from `RESPONSES` (2 variants per intent, chosen by `hash(message)`)
- Persists session messages to `chatbot_messages` table (via backend controller)
- No external LLM dependency — fully offline

| POST | `/chat` | Send message, get intent + reply |
| GET | `/health` | Service health check |

```json

  "session_id": "uuid-string",
  "user_id": 3 }
```

### SafeRent Score Formula
Weighted composite 0–100 (higher = safer):

| Factor | Weight |
|--------|--------|
| Disaster Risk (inverted) | 30% |
| Flood Risk (inverted) | 20% |
| Landslide Risk (inverted) | 15% |
| Hospital Access | 10% |
| Transport Access | 10% |
| Crime Safety | 10% |
| Rainfall (normalised) | 5% |

## Quick Comparison

| Service | Port | Saved Model | Algorithm | Training Data | Real or Synthetic? |
|---------|------|-------------|-----------|---------------|---------------------|
| Recommendation | 8001 | `profile_model.joblib` + `property_features.joblib` | 2-stage: RF profile→criteria + weighted similarity | 10,000 synthetic + live properties (Stage 2) | Synthetic (Stage 1) |

at training time — never retrains, never touches the service's `app.py` or training
script) that regenerates the report figures in that service's `outputs/` folder. Added
2026-08-30 to give the report a defensible, reproducible evaluation section for every
model rather than only Location Intelligence.
